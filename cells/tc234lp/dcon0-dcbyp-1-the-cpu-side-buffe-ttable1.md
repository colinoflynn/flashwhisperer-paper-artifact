### Where the line offset came from

DERIVED, not quoted. Row width 32 B from DATASHEETS.md *Measured on this bench* table A, the **flash read width** column -- NOT the neighbouring depth-times-granularity column, which reads '>=3 rows reachable x 32 B' and is the buffer depth. Re-measured in the same session by the rig's own alternating-read probe: 17.008 cyc/pair below gap 32, **21.007 at gap 32**, 22.008 at 64, so the row is 32 B. Entries per row is the row width over the ATTACKED table's entry size, and the last-round attack partitions the 256 B byte S-box -- every implementation in this rig, the T-tables included, ends with a byte-S-box round 10 -- so 32 B / 1 B = 32 entries and line_shift = 5. line_off is in entries: (0x80001240 mod 32) / 1 = 0. Te0's own geometry is line_shift 3 at line_off 0 (32 B over 4-byte entries) and is recorded per capture in the `te0_addr` field, but it is not the partition the attack uses. line_shift 3 ALSO recovers, slightly worse at every offset, because an 8-entry partition is a strict refinement of a 32-entry one -- that is nesting, not evidence for a 4-byte row.
